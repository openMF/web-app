# WEB-1258 End-of-Day Cash Closing API

The Web App calls the Savings Plugin at `/v2/base-teller/end-of-day-closing` through the configured Fineract API host. The host adds `/fineract-provider/api` locally. The contract below comes from `EndOfDayClosingApiResource`, `EndOfDayClosingRequest`, `EndOfDayClosingData`, and `EndOfDayClosingPlatformService` in the WEB-1258 Savings Plugin branch.

| Method | Path                                         | Permission                                                                       | Purpose                                                                                            |
| ------ | -------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| GET    | `/context`                                   | `READ_BASE_TELLER_END_OF_DAY_CLOSING`                                            | Business date, accessible cashiers, configured currencies and denominations, completed closing IDs |
| GET    | `/checks?cashierId={id}&currencyCode={code}` | `READ_BASE_TELLER_END_OF_DAY_CLOSING`                                            | Eligible check objects; currency filter optional                                                   |
| POST   | `/preview`                                   | `CREATE_BASE_TELLER_END_OF_DAY_CLOSING`                                          | Recalculate the declaration from current inventory and eligible checks                             |
| POST   | `/`                                          | `CREATE_BASE_TELLER_END_OF_DAY_CLOSING` plus valid Primary Cashier authorization | Complete and settle once                                                                           |
| GET    | `/{id}`                                      | `READ_BASE_TELLER_END_OF_DAY_CLOSING`                                            | Return stored closing snapshot                                                                     |
| GET    | `/{id}/report`                               | `REPRINT_BASE_TELLER_END_OF_DAY_CLOSING`                                         | Return the same stored snapshot for print and reprint                                              |

`context` returns `{businessDate, cashiers, currencies, completedClosingIds}`. A cashier has `cashierId`, `staffId`, `cashierName`, `tellerId`, `tellerName`, `officeId`, `officeName`, and `closed`. A currency has `currencyCode`, `decimalPlaces`, and `denominations`. Each denomination has `denominationId`, `type`, `value`, `quantity`, and `amount`. The UI renders every returned currency and denomination. The backend accepts `COIN` and bill types `BILL`, `BANKNOTE`, and `NOTE`.

`checks` returns an array of `{source, id, date, currencyCode, type, bank, reference, username, cashierId, amount}`. Selection identity is the pair `{source, id}`. The backend rechecks eligibility at preview and completion. Check status is not changed by the UI.

The preview body is `{cashierId, businessDate, idempotencyKey, currencies}`. Each currency declaration is `{currencyCode, denominations: [{denominationId, quantity}], vouchers, checks: [{source, id}]}`. Every configured currency must occur exactly once. Quantities are nonnegative integers. Voucher amounts follow that currency's precision. The idempotency key is a UUID that remains stable when retrying an unchanged declaration. Preview does not persist a closing. No expected balance or discrepancy is submitted by the UI.

Completion sends the same declaration plus `{authorization: {username, credential}}`. The username and credential belong to an eligible Primary Cashier with `AUTHORIZE_BASE_TELLER_END_OF_DAY_CLOSING`; the authorizer must be distinct from the cashier and caller and satisfy the backend office and allocation checks. The password input is cleared immediately after submission and on dialog destruction. A duplicate completion with the same key and declaration returns the stored closing. A key reused with a changed declaration conflicts. The backend takes a fresh authoritative snapshot at completion, including current check eligibility and expected balances.

Preview, completion, retrieval, and report share the `EndOfDayClosingData` shape. It includes `id`, `reference`, `status`, `businessDate`, office/teller/cashier identity, `createdBy`, `authorizedBy`, `authorizedByUsername`, `authorizedAt`, `completedAt`, and `balancesByCurrency`. Each balance contains `expectedCash`, `expectedChecks`, `expectedVouchers`, `expectedTotal`, `coinTotal`, `billTotal`, `declaredCash`, `selectedChecks`, `vouchers`, `declaredTotal`, `shortage`, `overage`, `reconciliationStatus`, denomination and check snapshots, `reconciliationId`, and `settledCash`. Preview has `status: PREVIEW` and no closing ID. Completion has `status: COMPLETED` and a reference. `BALANCED`, `OVERAGE`, and `SHORTAGE` are all valid outcomes. Discrepancy is audit information; native settlement uses the authoritative expected balance.

The report endpoint returns the immutable completion snapshot. The print view uses only that response. The UI does not reconstruct historical financial values from forms or transaction history. Backend errors are mapped to safe translated messages; response bodies are never logged by this workflow.
