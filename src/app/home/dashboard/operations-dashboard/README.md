## Backend dependencies

Authoritative prospect-task stage entry/aging and pending aggregates, verified prospect/application associations, shared task ownership/review/assignment/stage transition, auditable recipient-qualified escalation, PLD decisions, collection contacts and a bounded collection follow-up feed remain necessary. Bulk assignment/escalation are unavailable until those per-resource contracts and permissions exist. Frontend navigation never records review, completion, escalation, contact or payment.

Enrollment activation is a client task, not evidence of an overdue prospect. Its start is unavailable. Prospect technical created/submitted/updated timestamps are never used as stage starts. Loan approval uses submittedOnDate; disbursement age remains unavailable because the projection lacks approved-on date. Invalid/future/missing dates and missing business date remain unknown. No mixed currencies or requested amounts are summed. No new financial calculations or endpoints are introduced.

Existing analytics remain available through a separate lazy tab; their pre-existing fallback behavior is outside this change. Operations never instantiates those adapters. Existing board navigation is preserved; links into Operations use qualified resource keys, never names. Commercial prospect identity and enrollment client identity stay separate.

## Report-definition audit

Fineract `fineract-provider/src/main/resources/db/changelog/tenant/parts/0002_initial_data.xml` and `0003_postgresql_specific_initial_data.xml` define **Portfolio at Risk**. Its active-loan outstanding/overdue sums and `parType` ratios are not a PAR 30 calculation: there is no 30-day cohort filter or business-date/as-of parameter. Currency rows are grouped by loan currency code but expose `Currency` as a display symbol where present. Without the deployed institutional risk definition, date and ISO currency/scope contract, it is unsafe to label that output PAR 30 or an unqualified current portfolio total. Tenant report definitions can differ from seeds.

`0087_update_dashboard_table_reports.xml` defines **Demand Vs Collection** as lifetime schedule sums (`AmountDue`, `AmountPaid`). It has no today transaction filter and aggregates across currencies. It cannot supply posted non-reversed collections today or today's due amount. Per-loan repayment schedules, notes and loan/client staff/officer assignment operations were inspected; they do not establish a global collections queue or task assignment/review/escalation semantics.

## Navigation and data limits

The original three tabs are preserved; existing analytics are a fourth lazy tab. Content persists across tab switches to avoid duplicate reads and preserve board state. Qualified links use `prospect:<id>`, `loan:<id>:approval`, `loan:<id>:disbursement` or `enrollment:<clientId>:ACTIVATION`. Loan and client-stage links outside the loaded pages use one authorized existing loan-detail or filtered enrollment read. They revalidate the exact returned resource and pending state before adding the real task to the loaded workspace. Selection never matches a name. Prospect search has no exact prospect-ID lookup; a commercial link outside the loaded prospect page displays a truthful unavailable message. It never selects an unrelated customer. Adding exact prospect-ID lookup is a remaining backend dependency.

Client activation tasks use their own `onboarding` area. They are not labelled as prospects and are excluded from the loaded prospect total and prospect-rule evaluation. Registration and client-stage counts are separately labelled page observations, not global unique prospect counts. Page cursors remain separate; the workspace loads at most 25 records per source, plus at most one exact requested task. Only the verified approval server total is displayed as a full queue count. Terminal, unknown-state and unauthorized records do not become tasks.

## Files and implemented behavior

- `operations-dashboard.component.{ts,html,scss}`: three cards, unavailable-rule notice, source-scoped counts, business-date aging, loaded-task search/age/area filters, accessible single-task selection, status details, authorized read navigation, bounded loan audit activity/history, error/empty/loading/denied states and 390/768/1280/1920px layouts in both themes.
- `operations-task.model.ts` and `operations-data.service.ts`: typed task/queue/audit adapters, strict response and date validation, permissions, bounded reads, exact qualified resource lookup, stale-request cancellation and tenant/user/business-date invalidation. No writes, automatic retries, random amounts, monetary aggregation, escalation automation or invented history.
- Parent Dashboard and existing board templates/models: tab integration and qualified links only. WEB-1480's unmerged redesign is not copied.
- Four new focused Jest suites; updated parent-tab regression test; operations Playwright configuration/spec; existing commercial Playwright setup adjusted for Operations' initial read.
- Every one of the 14 shipped locale catalogs: 89 Operations labels/messages each. Existing labels are reused where available.

## Acceptance limitations

This implementation completes the supported frontend scope. It does **not** meet the requirements for global prospect counts, prospect ten-day breach detection/Show them, automatic escalation, portfolio/PAR 30/collection monetary metrics, collection follow-up tasks, task ownership/Only mine, review/assignment/stage/compliance/contact mutations or bulk writes. Their precise missing contracts are above; controls and metrics remain unavailable. No write or confirmation is simulated. Full prospect/task audit history and system/human classification also require a feed beyond the loan audit fields available here.

The missing Jira DOCX, live tenant integration, remote CI and human approval are not certified. Screenshots use deterministic synthetic API fixtures. Repository instructions still require the contributor's manual before/after screenshots for PR approval.
